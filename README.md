# Клуб бадминтона

Рабочее приложение: **React + Vite + TypeScript** на фронтенде, **Node.js + Express** на сервере, **PostgreSQL + Prisma** для данных. Фронтенд можно разместить на обычном хостинге REG.RU, API — отдельно на Amvera. Развёртывание и платные сервисы автоматически не подключаются.

## Что работает

- Главная, форматы тренировок, тренеры, площадки, контакты, расписание с фильтрами и выбором дня.
- Регистрация по имени/email/паролю, вход/выход через Passport Local, серверные сессии express-session в PostgreSQL. Телефон — контакт, без SMS.
- Запись на групповую, индивидуальную и детскую тренировку (имя и возраст ребёнка из аккаунта родителя).
- Кабинет: предстоящие занятия, история, отмена, атомарный перенос, профиль, смена пароля. По умолчанию отмена/перенос доступны за 12 часов; правило меняется в настройках.
- Админка: показатели из БД, занятия и серии, участники и контакты, ручная запись клиента/гостя, отмена/перенос, посещения/пропуски, поиск клиентов, тренеры, площадки/корты, настройки, журнал изменений.
- Конкурентная запись защищена транзакционным advisory lock PostgreSQL, действующим между экземплярами API. Частичный уникальный индекс защищает активного участника; exclusion constraints запрещают пересечения корта и тренера даже на уровне БД.
- Перенос отменяет старую запись и создаёт новую в одной транзакции. При ошибке исходная запись сохраняется. История не удаляется.
- UTC-время в БД, отображение и серии в часовом поясе клуба (`Asia/Vladivostok` по умолчанию). Цены — целые копейки.

## Локальный запуск (Windows / macOS / Linux)

Требуются **Node.js 22.12+**, npm, Git и PostgreSQL 17 (локально, через Docker Desktop или на отдельном сервере).

```powershell
git clone https://github.com/bubnovdemid31-cmd/Badminton_zapis.git
cd Badminton_zapis
npm ci --ignore-scripts
Copy-Item .env.example .env
```

На Linux/macOS вместо `Copy-Item`: `cp .env.example .env`.

Отредактируйте `.env`:

- `POSTGRES_PASSWORD` — собственный пароль для локального Docker. В `DATABASE_URL` укажите **тот же пароль** (спецсимволы в URL нужно URL-кодировать).
- `DATABASE_URL` — строка подключения к PostgreSQL. `.env` никогда не попадает в Git.
- `SESSION_SECRET` — случайная строка не менее 32 символов. Сгенерировать:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

- `WEB_ORIGIN=http://localhost:5173` — точный адрес фронтенда, без завершающего `/`.

Если используете Docker Desktop:

```powershell
docker compose up -d db
```

После готовности БД:

```powershell
npm run db:generate
npm run db:migrate
npm run db:seed
npm run admin:create
npm run dev
```

Откройте **http://localhost:5173**. API работает на порту 3001; Vite проксирует `/api` автоматически. Сервер и фронтенд запускаются одной командой. Название, контакты и адрес меняются в админке.

`db:seed` добавляет явно помеченные демопрофили и 12 будущих тренировок. Не создаёт пользователей, администраторов или паролей, не перезаписывает настройки. Повторный запуск в тот же день не дублирует занятия. Не используйте seed на наполненной рабочей базе без необходимости.

### Создать первого администратора

```powershell
npm run admin:create
```

Команда спросит email, имя и пароль (ввод пароля скрыт). Минимум 12 символов. Существующий аккаунт не повышается до администратора по совпадению email. Публичная регистрация всегда создаёт клиента.

Для защищённого CI/консоли хостинга команда принимает `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD` из переменных процесса. Пароль не указывайте аргументом командной строки и не сохраняйте в репозитории. В Docker после запуска: `node dist/scripts/create-admin.js`; для демоданных — `node dist/prisma/seed.js`.

## Проверки

```powershell
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

`npm test` создаёт **отдельную БД с суффиксом `_test`** (по умолчанию `badminton_test`), применяет миграции и очищает данные **только в ней**. У пользователя PostgreSQL должно быть право создавать БД. Можно заранее создать тестовую БД и задать `TEST_DATABASE_URL`; имя обязательно оканчивается на `_test`. Никогда не указывайте рабочую базу как тестовую.

Интеграционные проверки используют настоящую PostgreSQL: последнее место в конкурентных запросах, дубли, освобождение места, срок отмены/переноса, атомарность переноса, пересечения тренера/корта/клиента, детские и гостевые записи, лимиты вместимости, серия с конфликтами, серверные права, CSRF и ограничение попыток входа.

Playwright запускает собранный сайт на порту 4173 и выполняет сценарий на компьютере и телефоне: регистрация → возврат к выбранному занятию → запись → перезагрузка → профиль → отмена → история. **Он создаёт тестовые аккаунты в БД из `DATABASE_URL`**. Для браузерных проверок используйте отдельную демобазу с будущими групповыми занятиями (`db:seed`). Не запускайте браузерные тесты на production. Скриншоты и трассы сохраняются в `test-results/` (не коммитятся).

Если Chromium уже установлен, можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. CI в GitHub Actions выполняет проверки автоматически; он не публикует сайт.

## REG.RU: фронтенд

1. Настройте домен, например `club.ru`, и HTTPS на хостинге.
2. При сборке задайте `VITE_API_URL=https://api.club.ru` (это публичный адрес, не секрет).

```powershell
$env:VITE_API_URL="https://api.club.ru"
npm run build:web
```

На Linux/macOS: `VITE_API_URL=https://api.club.ru npm run build:web`.

3. Загрузите **содержимое `dist/web/`**, включая `assets/` и `court.svg`, в корень сайта на хостинге. `dist/server/`, исходники и `.env` на публичный хостинг не загружайте.
4. Навигация использует hash-маршруты (`/#/schedule`), поэтому переадресация всех URL на `index.html` в панели хостинга не требуется.
5. При изменении адреса API нужно пересобрать фронтенд: Vite подставляет переменные во время сборки.

## Amvera: API и PostgreSQL

1. Создайте PostgreSQL и приложение с Dockerfile из корня репозитория. База должна поддерживать расширение **btree_gist**; пользователю миграций нужны права создания расширения/таблиц. Это требуется для ограничения пересечений.
2. В защищённых настройках приложения задайте `DATABASE_URL`, случайный `SESSION_SECRET`, `WEB_ORIGIN=https://club.ru`, `NODE_ENV=production`, `PORT=3001`, `TRUST_PROXY=1` при одном доверенном reverse proxy Amvera. Контейнер слушает `0.0.0.0:3001`; на платформе выберите тот же внутренний порт.
3. Подключите домен `api.club.ru` и HTTPS. Базу данных не публикуйте в Интернет без необходимости. Если провайдер требует TLS к БД, используйте его корректный CA/параметры PostgreSQL; проверку сертификатов не отключайте.
4. Dockerfile собирает проект, убирает dev-зависимости и при старте выполняет SQL-миграции, затем запускает API. Проверка готовности: `GET /api/health` проверяет доступ к БД.
5. Создайте администратора через консоль контейнера: `node dist/scripts/create-admin.js`. Демоданные при необходимости: `node dist/prisma/seed.js`.
6. Проверьте реальный HTTPS-вход, запись и отмену перед открытием сайта клиентам. Настройте резервное копирование PostgreSQL на платформе.

**Сессии:** HTTP-only cookies, в production только Secure. Рекомендуются `club.ru` + `api.club.ru`: это один site, `COOKIE_SAME_SITE=lax`. Для API на чужом домене понадобится `COOKIE_SAME_SITE=none` и HTTPS; некоторые браузеры блокируют такие сторонние cookies. Собственный API-поддомен надёжнее. CORS разрешает только точный `WEB_ORIGIN`; все изменяющие запросы также требуют CSRF-токен, получаемый фронтендом через `/api/auth/session`. Сессии переживают перезапуск API и общие для его реплик. После смены пароля другие сессии теряют доступ.

При необходимости можно размещать всё одним Node-приложением: установите `SERVE_WEB=1`, оставьте `VITE_API_URL` пустым во время сборки и используйте одинаковый домен для сайта и API.

## Миграции и структура

- `src/` — React-интерфейс; `public/court.svg` — авторская заменяемая иллюстрация (не фотография чужого клуба).
- `server/` — Express, сессии, API и доменные транзакции.
- `prisma/schema.prisma` — модели; `prisma/migrations/` — версионированный SQL, сгенерированный из Prisma и дополненный ограничениями PostgreSQL.
- `scripts/migrate.ts` — применяет SQL через `pg`, под advisory lock, каждую миграцию в транзакции. Сохраняет SHA-256 и отказывается применять изменённую старую миграцию. Используется вместо `prisma migrate deploy`, чтобы не скачивать нативный schema engine. Журнал — `_ClubMigration`.
- `prisma.config.ts` — JS-движок Prisma 6.19; конфигурация CLI-адаптера помечена Prisma как experimental. Клиент использует официальный `@prisma/adapter-pg`, нативные бинарники для работы API не нужны.
- Новые изменения схемы оформляйте **новой** SQL-миграцией; не меняйте уже применённые. Для генерации SQL: `npx prisma migrate diff --from-schema-datamodel old.prisma --to-schema-datamodel prisma/schema.prisma --script`. Просмотрите SQL и примените `npm run db:migrate`; не смешивайте два журнала миграций, не используйте `db push` на рабочей БД.

## Границы версии

Нет онлайн-оплаты, SMS, рассылок, абонементов и аренды корта без тренера. Оплата — в клубе. Нет восстановления пароля и подтверждения email; не выдаём эти функции за работающие. Контент, портреты-инициалы и иллюстрации демонстрационные, контакты должен заполнить клуб. Для реального запуска также нужны согласованные с владельцем тексты политики обработки персональных данных.

Листы API ограничены: расписание — 300 будущих занятий, админские списки — 500 записей/занятий, поиск клиентов — 200 результатов, журнал — 100 последних действий. Серии ограничены 181 днём; пагинация и массовая рассылка изменений не реализованы. История сохраняется полностью в БД. Блокировка записи глобальная: надёжна для небольшого клуба, при большой нагрузке стоит перейти к более мелким блокировкам с сохранением тестов инвариантов.

Автоматическая публикация на REG.RU/Amvera не настроена: push обновляет GitHub и запускает CI. На вашем ПК изменения забираются командой `git pull --ff-only`.
